About

Built to make phishing visible.

PhishSim AI is a security awareness platform that runs simulated phishing campaigns against your own organization — so your team encounters realistic attacks in a controlled environment before a real adversary gets the chance. It generates personalized lure emails using an AI engine, tracks click and submission behavior per recipient, and produces a risk report with department-level breakdowns. The goal isn't to embarrass people who click. It's to give security teams actual data instead of checkbox compliance.

What the platform does

You configure a campaign — target list, scenario type (CEO impersonation, IT credential harvest, HR payroll, urgent invoice), urgency level. The AI engine generates a unique phishing email for each recipient, referencing their name, department, and company context. Emails are dispatched through your configured relay, and a tracking pixel plus unique link per recipient captures opens, clicks, and credential submissions without storing any real credentials.

Once a campaign runs, the dashboard shows who clicked, who reported, who submitted — broken down by department. The AI Risk Advisor cross-references that with OSINT signals (DMARC health, subdomain exposure, breach data) to estimate actual organizational exposure. Spot the Phish and the email header analyzer are standalone training tools that work without running a full campaign.

Everything that touches real user data is session-scoped and campaign-scoped. There's no persistent credential storage, no cross-org data sharing, and the simulation landing pages are clearly marked after the fact to close the loop for the recipient.

Tech stack

The backend is Flask. AI email generation calls OpenRouter's API, which proxies a pool of free-tier language models — DeepSeek, Gemma, Llama, Mistral. The generation logic races the top-N models in parallel threads and returns the first successful response, keeping latency down even when individual models are slow or unavailable. Static fallback templates cover the case where the API key is missing or all models fail.

One real bug story

The chatbot mascot, Lure, lives in a floating panel that can be in several states: idle, thinking, success, error, tour mode, minimized. Each state applies different classes and glow styles to a single host element, #pb-host.

The bug: During walkthrough tour mode, the mascot would flash the wrong glow color or get stuck on error state even after the tour completed cleanly. The root cause was that six different functions — _doGenerate, startTourMode, endTourMode, the chat handler, the tab switcher, and the success flash — were all writing directly to host.className independently. Two of them would fire in quick succession during tour completion and stomp each other's state.

Before — scattered direct writes
// in _doGenerate:
host.className = 'pb-success';

// in endTourMode (200ms later):
host.className = 'pb-idle';

// in success flash (300ms later):
host.className = 'pb-success';
// Race. Last write wins.
After — single setHostState()
function setHostState(visual, opts) {
  const host = getHostEl();
  host.classList.remove(...ALL_STATES);
  host.classList.add(`pb-${visual}`);
  if (opts?.revertAfter) {
    scheduleRevert(opts.revertAfter);
  }
}
// One writer. No races.

Centralizing all state transitions through setHostState() meant one place to enforce transition logic — including a queued revert timer that cancels itself if a new state is set before it fires. Every caller that previously wrote host.className = … directly became a setHostState(…) call. The tour-mode flicker disappeared, and success/error glows now always revert to idle correctly regardless of what else is running concurrently.

The broader lesson wasn't surprising — direct DOM mutation scattered across unrelated functions behaves fine until timing matters. A state machine with a single writer is worth the refactor cost even in vanilla JS.
